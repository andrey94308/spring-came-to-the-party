# OrgArchive — опорные заметки (RU)

Черновик для обсуждения. Это темы и ключевые фразы, а не текст для чтения слово в слово.

## 1. Короткое вступление

- Покажу, как две уязвимости библиотек и решения в коде складываются в одну цепочку.
- Для этого я собрал небольшой демо-проект — OrgArchive.
- Сначала устройство и ожидаемая защита. Затем код и Postman.

## 2. Что делает OrgArchive

- Организации хранят документы. Пользователь видит документы только своей организации.
- Администратор отвечает за учётные записи. В этом прототипе он может получить список пользователей или данные одного пользователя.
- У пользователя есть внутренний `organizationUuid`. У документа тот же идентификатор лежит в JSON-метаданных вместе с `category` и `revision`.
- MariaDB 11.8 поддерживает векторы. В будущем можно добавить поиск похожих документов по эмбеддингам текста.
- Сейчас векторов и эмбеддингов нет. Реализован обычный поиск по метаданным. Spring AI переводит `Filter.Expression` в условие SQL для MariaDB.
- Векторный поиск относится к содержимому документа. Метаданные дают точные дополнительные фильтры.

## 3. Схема системы и маршрутов

- Клиент → Archive Service на `localhost:8080` → MariaDB в Docker.
- `POST /signup` — публичная регистрация; сервер создаёт обычного пользователя и назначает новый UUID организации.
- `GET /users`, `GET /users/{id}` — вход обязателен; предполагается роль `ADMIN`.
- `GET /organizations`, `GET /organizations/{id}` — второй набор админских запросов; в Postman не используется.
- `POST /documents/search` — вход и роль `USER`; организация берётся из учётной записи, а не из запроса.
- `/documents/search-safe` и `/documents/search-debug` — дополнительные маршруты для сравнения в демо.
- `GET /` — открытый индекс всех маршрутов самого сервиса; подписи показывают задуманную защиту.

## 4. Как задумана защита

- Показать `SecurityConfig`: HTTP Basic; `/` и `/signup` доступны без входа. Остальные маршруты требуют аутентификации.
- Пароли хранятся как BCrypt-хеши. Роль не хешируется: Spring Security использует её для проверки `USER` и `ADMIN`.
- Показать `AdminRoleSecurityContract`: общий интерфейс для `list` и `get`; на обоих методах стоит `@PreAuthorize("hasRole('ADMIN')")`.
- Показать `DocumentController` и `DocumentSearchService`: `@PreAuthorize("hasRole('USER')")`; UUID организации читается на сервере.
- В норме клиент не выбирает чужую организацию. UUID не возвращается при регистрации.

## 5. Заметная слабость в коде

- Показать `UserController`: `GET /users?debug=true` возвращает BCrypt-хеши паролей.
- На первый взгляд риск можно недооценить: маршрут задуман только для администратора, пароли не в открытом виде.
- Похожие старые debug-решения встречаются на практике. Здесь оно сделано намеренно для демо.

## 6. Уязвимости и цепочка

- **CVE-2025-22223:** уязвимая версия Spring Security пропускает проверку роли, объявленную на параметризованном интерфейсе. Вход всё ещё нужен; обычный пользователь получает админский список без роли `ADMIN`.
- Флаг `debug=true` открывает хеш Анны. Её слабый пароль можно подобрать локально по короткому словарю. В Postman он уже задан.
- Анна ищет свои документы с фильтром `category=report`. Нормальный поиск остаётся внутри её организации.
- **CVE-2026-22730:** конвертер Spring AI вставляет значение `category` в SQL без правильного экранирования. Добавленное `OR` обходит условие организации; появляются чужие документы.
- `search-safe` передаёт значения как параметры SQL. Тот же ввод не меняет структуру запроса.

## 7. Демонстрация и вывод

- Postman: анонимный запрос → регистрация → первый доступ к `/users` → хеши → вход как Анна → обычный поиск → SQL-инъекция → безопасное сравнение.
- Проверять не только наличие CVE, но и достижимость уязвимого пути в своём приложении.
- Старые решения в коде могут резко увеличить последствия новой CVE. Оценивать цепочку целиком и вовремя обновлять зависимости.
