## 2. OrgArchive: данные и поиск

- В OrgArchive разные organizations хранят documents.
- User должен видеть documents только своей organization. Admin может смотреть users и organizations.
- У каждого user и document есть `organizationUuid` в отдельной колонке. Это связь с organization. В JSON-метаданных документа лежат `category` и `revision`.
- MariaDB 11.8 выбрана так как поддерживает векторы и так можно реализовать векторный поиск по тексту документов.
- По этой же причине используется Spring AI который нужен для связки векторного поиска с базой данных
- В реализации я использую только малую часть Spring AI для фильтрации по метаданным.

## 3. Маршруты: что доступно клиенту

- `GET /v3/api-docs` публикует OpenAPI-спецификацию: в ней видны пути и HTTP-методы. Это описание API, а не доступ к данным.
- `POST /signup` открыт. Он создаёт user и новый внутренний `organizationUuid`; в ответе только username.
- `GET /users` и `GET /users/{id}` предназначены для admin. `GET /organizations` и `GET /organizations/{id}` используют то же правило.
- `POST /documents/search` доступен user. UUID его organization сервер берёт из учётной записи, а не из запроса.
- `search-safe` покажет безопасное сравнение после SQL-инъекции. `search-debug` существует для демо, но в основной цепочке не нужен.

## 4. Код: где проверяется доступ

- Открою `SecurityConfig`. HTTP Basic проверяет логин и пароль. Без входа доступны только `/signup` и OpenAPI.
- Для `/users`, `/organizations` и `/documents` HTTP-фильтр требует аутентификацию. Затем проверяется роль на методе.
- Открою `AdminRoleSecurityContract`. Интерфейс задаёт `list` и `get`; оба метода имеют `@PreAuthorize("hasRole('ADMIN')")`.
- `UserController` и `OrganizationController` реализуют этот общий интерфейс. Так они должны получать одно правило для admin-запросов.
- Открою `DocumentController`: для поиска нужен `USER`. В `DocumentSearchService` UUID берётся из аккаунта вошедшего user.
- Пароли в базе хранятся как BCrypt-хеши. Роли `USER` и `ADMIN` используются для проверки доступа.

## 5. Код: слабое debug-решение

- В `UserController` обычный `GET /users` не возвращает пароли. Но `GET /users?debug=true` возвращает `passwordHash` каждого user.
- Это намеренная слабость демо. Подобный старый debug-код можно встретить и в реальных проектах.
- Сначала риск кажется небольшим: endpoint предназначен для admin, а пароли представлены хешами.

## 6. Две CVE

- CVE-2025-22223: Spring Security в используемой версии может не увидеть `@PreAuthorize` на параметризованном интерфейсе.
- HTTP-фильтр всё ещё требует вход. Но обычный зарегистрированный `USER` получает admin-список `/users` без роли `ADMIN`. Это первый несанкционированный доступ.

- CVE-2026-22730: конвертер Spring AI вставляет значение `category` в SQL без правильного экранирования. SQL-условие с `OR` обходит фильтр organization.
- После инъекции ответ содержит documents других organizations.
